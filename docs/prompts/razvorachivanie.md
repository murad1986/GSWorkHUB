# Промпт: развернуть склад и собрать в него весь текущий контекст

Вставляется целиком в агента (Codex CLI, Claude Code — любой, у кого есть доступ
к файлам репозитория и к вашим MCP-серверам), запущенного в корне GSWorkHUB.
Работа занимает несколько часов и делится на семь шагов; после каждого агент
останавливается и показывает результат.

---

Ты разворачиваешь рабочую операционную систему GSWorkHUB на этой машине.
Склад — обычные markdown-файлы под git: `raw/` события, `work/` позиции,
`wiki/` сводки. Правила поведения — в `AGENTS.md`, устройство типов и полей —
в `docs/storage-schema.md`. Прочитай оба файла до начала работы и дальше
сверяйся с ними, а не с общими соображениями.

**Границы, которые не обсуждаются.**

- Наружу ты не пишешь ничего: ни сообщений, ни комментариев, ни ответов в чатах,
  ни изменений в чужих документах. Только чтение.
- `raw/` не редактируется никогда. Ошибка исправляется новой записью.
- Ты не выдумываешь участников, даты, сроки, владельцев и цитаты. Источник не
  дал — поле остаётся пустым.
- Решения, деньги, сроки и обязательства перед людьми ты приносишь человеку на
  подтверждение, а не записываешь сам.
- После каждого шага показываешь результат и ждёшь ответа. Не переходи к
  следующему шагу молча.

---

## Шаг 1. Проверить, что система жива

```bash
python3 -m pip install -r requirements.txt
make gates
```

Обе строки обязаны быть зелёными: `VERIFY: сошлись все N случаев` и
`ЛИНТ: чисто`. Красный линт на чистой копии — стоп: разберись до продолжения и
покажи вывод человеку.

Затем `make check-env` — покажи, что на этой машине есть, а чего нет.

**Покажи:** вывод обеих команд как есть, без пересказа.

## Шаг 2. Завести владельца склада

Спроси у человека имя, роль и как к нему обращаться. Затем:

- переименуй `work/people/ivan-petrov.md` под него, поправь имя и роль;
- поправь `work/me/me.md` — поле `person` ведёт на эту карточку;
- открой `work/me/profil.md` и задай **по одному** пять вопросов из заготовки:
  где сильное, где слабое, как принимаются решения, когда решениям верить, каким
  тоном поднимать зависшее. Записывай ответы его словами, не своими.

Профиль заполнять необязательно сразу — но пустым он должен остаться честно, а
не быть заполненным твоими догадками.

```bash
make index && make lint
```

**Покажи:** карточку человека и профиль; спроси, всё ли верно.

## Шаг 3. Подключить интеграции — по одной, с проверкой каждой

Ключи кладутся в `config/secrets.env` (образец — `config/secrets.env.example`).
Файл в git не попадает. Подключай по очереди и после каждой сразу проверяй:

| Источник | Что нужно | Проверка |
|---|---|---|
| Telegram — разговорный вход и голос | токен бота от `@BotFather` в `TELEGRAM_BOT_TOKEN`, числовой id владельца в `TELEGRAM_ALLOWED_USER_ID` | `make telegram ACTION=check` |
| Расшифровка голоса | `DEEPGRAM_API_KEY` | приходит с первым голосовым |
| Календарь | доступ Google | `make calendar` |

Затем — источники, доступные только через MCP. Перечисли, что есть:

```bash
codex mcp list
```

Для каждого рабочего сервера (диктофон Plaud, переписка, документы, базы,
трекеры, доски) проверь, что он отвечает: возьми одну свежую запись и покажи
человеку, что именно видишь. Дальше все они работают через общий вход —
`tools/capture.py`, описание в `docs/connector-plaud.md`.

Ни одна интеграция не обязательна: без ключа склад работает целиком, молчит
только соответствующий вход. Не подключай то, к чему нет доступа, и не
придумывай обходных путей — скажи, чего не хватает.

**Покажи:** таблицу «источник — подключён/нет — чем проверено».

## Шаг 4. Спросить, что вообще есть

До того как тянуть данные, выясни у человека рамку. Один вопрос за раз:

1. Какие клиенты и проекты идут прямо сейчас? Названия и кто по ним главный.
2. Где лежит рабочая переписка — какие каналы и чаты считать рабочими?
3. Где живут документы: диск, база знаний, доски?
4. За какой период имеет смысл поднимать историю — месяц, квартал, год?
5. Что заведомо не надо тянуть: личное, чужое, архив?

Ответы запиши как источник в `raw/sources/<дата>-ramka-sbora.md` — это событие,
на которое ты будешь ссылаться дальше.

**Покажи:** список того, что собираешься собрать, с оценкой объёма.

## Шаг 5. Собрать историю — партиями, от свежего к старому

Первичный сбор отличается от ежедневного только объёмом. Порядок: свежее
сначала — оно нужнее; старое подтягивается, пока есть смысл.

Для каждого источника приведи записи к общему виду и передай в приём:

```bash
python3 tools/capture.py --file partiya.json
```

Формат — список объектов; обязательны `source`, `external_id`, `date`, `title`:

```json
[{"source": "plaud",
  "external_id": "rec_8123",
  "date": "2026-08-14",
  "title": "Планёрка по маршрутам",
  "body": "<дословное содержимое: расшифровка, переписка, документ>",
  "revision": "<версия, если источник её даёт>",
  "fields": {"container": "work/clients/<кто>", "participants": ["Имя"]}}]
```

Правила, которые нельзя нарушать:

- **`source` пишется одинаково всегда.** `plaud` и `Plaud` — один источник,
  `plaud-app` — уже другой, и один разговор ляжет дважды.
- **`external_id` берётся из источника**, а не выдумывается. Нет его — собери из
  неизменных признаков: канал, дата, точное время начала.
- **`body` — дословно.** Не пересказывай, не сокращай, не «улучшай». Пересказ
  делает разбор, а он ещё не начался.
- **`container` — только когда принадлежность названа в самой записи.**
  Неочевидно — не ставь: пустое поле честнее выдуманного.
- **Партия — 20–50 записей.** После каждой: `make lint`. Красный линт — разберись
  до следующей партии.
- **Повторы отбрасываются сами** по паре «источник + версия». Захватить лишнее
  безопаснее, чем потерять.

Не тяни в склад живые документы, которые постоянно правятся снаружи: для них
есть поле `mirror` — адрес живой копии. Копия в складе разойдётся с оригиналом
за неделю.

**Покажи после каждого источника:** сколько записей пришло, сколько принято,
сколько отброшено повторами, что не удалось и почему.

## Шаг 6. Разобрать первую волну

Приём закончен — начинается разбор, и здесь правила строже. Разбирай **по
одному источнику**, четырьмя проходами: факты → противоречия → причины →
следствия (раздел 3 в `AGENTS.md`). Вывод, сделанный до того как выписаны
факты, всегда подгоняется под вывод.

Заведи контейнеры под то, что реально идёт:

- клиент — `work/clients/<имя>/client.md` со своим префиксом ключей;
- программа или внутренний проект — `work/programs/<имя>/`;
- люди, которые встречаются в записях, — `work/people/`.

Из разобранного предлагай позиции: обязательства (`commitment`), открытые
вопросы (`question`), риски (`risk`), процессы (`process`), решения
(`decision`). Каждая позиция обязана ссылаться полем `origin` на событие в
`raw/`, из которого она взялась.

**Каждую позицию показывай человеку целиком до записи**: формулировка,
ответственный, срок, следующий шаг, ссылка на источник. Он подтверждает — ты
записываешь. Он поправляет — записываешь поправленное, а не своё.

Не заводи позиции из размышлений вслух. Замысел, который перечёркивается одним
словом другого человека, — ещё не замысел: он остаётся событием в `raw/`.

Учебные записи — клиент «Альфа», Анна Смирнова, встреча 3 августа — удали,
когда появятся настоящие:

```bash
rm -rf work/clients/alfa work/people/anna-smirnova.md work/ideas/shablon-priema-zayavok.md
rm raw/meetings/2026-08-03-* raw/interviews/2026-08-05-* raw/observations/2026-08-05-* raw/sources/2026-08-01-alfa-*
make index && make lint
```

**Покажи:** не больше трёх находок за раз, каждая — норма, факт, причина,
последствие, что делать (раздел 4 в `AGENTS.md`). Остальное — по запросу.

## Шаг 7. Поставить автосбор и закрыть развёртывание

```bash
make context DRY=1     # проверить обход вхолостую
make context           # первый настоящий обход
```

Затем поставь расписание на три захода в сутки по инструкции
`docs/avtosbor-konteksta.md` (launchd на macOS, cron на сервере) и убедись, что
первый заход отработал: `~/Library/Logs/GSWorkHUB/context.log`.

Закрывающая проверка:

```bash
make gates && make welcome && make today
```

**Покажи человеку итог:**

- какие источники подключены и какие остались без доступа;
- сколько событий в складе и за какой период;
- какие контейнеры заведены и сколько в них открытых позиций;
- что показывает `make today` завтра утром;
- три вещи, которые ты не смог сделать, и что для них нужно.

Закоммить всё одним понятным коммитом. Дальше система живёт обычным циклом:
утренний вход, работа, `make gates` перед коммитом.
