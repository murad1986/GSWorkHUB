# Plaud и другие источники через MCP

Диктофон Plaud, переписка, документы, доски — источники, у которых в складе нет
собственного коннектора. Их приносит агент через свои MCP-серверы, а склад даёт
им один общий вход: `tools/capture.py`.

Такое разделение осознанное. Коннектор внутри склада нужен там, где API
стабилен и его стоит держать своим кодом (календарь, задачи). Там, где данные
уже доступны агенту, писать второй клиент — двойная работа: агент читает через
MCP, а склад отвечает за правила приёма — что считается повтором, куда ложится
файл, какие поля обязательны.

## Общий вход

```bash
make capture FILE=vhod.json          # принять
make capture FILE=vhod.json DRY=1    # сказать, что было бы принято
```

Формат — объект или список объектов:

```json
[{"source": "plaud",
  "external_id": "rec_8123",
  "date": "2026-08-14",
  "title": "Планёрка по маршрутам",
  "body": "## Расшифровка\n\n**Иван:** …",
  "revision": "2",
  "aliases": ["plaud-note-8123"],
  "fields": {"container": "work/clients/alfa", "participants": ["Иван Петров"]}}]
```

Обязательны четыре поля: `source`, `external_id`, `date`, `title`. Неполная
запись останавливает приём с внятной ошибкой — молча пропущенной записи не
бывает.

Каждая принятая запись ложится в `raw/inbox/` файлом типа `source` с шапкой, где
`source_ref` собран из `external_id` и `revision`.

## Как узнаётся повтор

По паре «источник + идентификатор версии». Запуск дважды подряд не создаст
второй копии; изменившаяся запись приходит **новой версией** — тот же
`external_id`, другой `revision`, — и это новое событие, а не правка старого.
Уже записанный файл не открывается на запись никогда.

Отсюда правило именования: `source` пишется одинаково от захода к заходу. `plaud`
и `Plaud` система считает одним источником, а `plaud-app` — уже другим, и тогда
один разговор ляжет дважды.

## Plaud

У Plaud нет открытого API склада; данные берёт агент через MCP-сервер, который
уже настроен в Codex. Проверить, что сервер виден:

```bash
codex mcp list
```

Дальше работает промпт [prompts/sbor-konteksta.md](prompts/sbor-konteksta.md):
агент перечисляет записи с прошлого захода, забирает расшифровки целиком и
передаёт их в приём. Расшифровка кладётся дословно — пересказ делает разбор, а
он начинается позже и человеком.

Полезные соответствия полей:

| Поле склада | Что из Plaud |
|---|---|
| `external_id` | идентификатор записи; нет — дата и точное время начала |
| `date` | дата записи, а не дата выгрузки |
| `title` | название записи; нет — первая строка сводки |
| `body` | расшифровка целиком, при наличии — со сводкой отдельным разделом |
| `revision` | версия расшифровки, если Plaud её меняет после дообработки |
| `fields.container` | клиент или проект — **только когда назван в самой записи** |

## Другие источники

Тот же вход годится для любого MCP: переписка, письма, документы, базы,
трекеры. Отличие только в `source` и в том, что считать одной записью:

| Источник | Одна запись | `external_id` |
|---|---|---|
| Переписка | разговор за сутки | канал + дата |
| Почта | письмо или цепочка | message-id или id цепочки |
| Документы | документ | id страницы, версия — в `revision` |
| Доски | доска целиком | id доски, версия — дата изменения |
| Трекеры | задача | id задачи, версия — дата изменения |

Документ, который правится постоянно, лучше брать не при каждом заходе, а по
изменению версии — иначе зона приёма наполнится сотней версий одного файла.
Живой документ, который читают и правят снаружи, вообще не копируется в склад:
для него есть поле `mirror` — адрес живой копии, см. конец
[схемы склада](storage-schema.md).
